サイト掲載のライセンス法文に、翻訳が名指しで derivative work に含まれている:

> "Derivative Work" means a work based upon the Work ... such as **a translation**, musical arrangement, dramatization, ...

> You may distribute ... a Derivative Work only under the terms of this License, **a later version of this License with the same License Elements** as this License, ...

→ **CC BY-NC-SA 4.0 は「同一 License Elements の後継版」に該当するため、4.0 での公開は継承条件を満たす。**

## 4. 次のセッションでやること（優先順）

### Step 1: 前提確認（ユーザーに聞く）

以下は未決定。作業開始前に `AskUserQuestion` で確認すること:

1. **リポジトリの置き場所** — 新規プライベートリポジトリを作るか、`onepagers` 配下のサブディレクトリにするか
   （新規リポジトリの場合、現セッションのスコープ外なので `add_repo` / 手動作成が必要）
2. **文体・一人称** — 語り手 Siri Keeton の一人称をどうするか（「私」／「ぼく」／「おれ」）、常体か敬体か
   → これは後から全体一括変更が困難なので**最初に決める**
3. **翻訳プラットフォーム** — GitHub PR のみで回すか、Weblate 等の翻訳 UI を併用するか
4. **訳者クレジットの方針** — 個人名義／ハンドル／匿名可、の扱い

### Step 2: 用語集とスタイルガイドを先に固める ★最重要

**コミュニティ翻訳が破綻する最大の原因は用語の不統一。** 本文着手より前にここを固める。

*Blindsight* は造語・固有名詞・専門用語が非常に多い。最低限、以下のカテゴリを洗い出して訳語を確定する:

- 宇宙船・地名・組織名などの固有名詞
- 作中の造語・生物名
- 神経科学／認知科学の専門用語（本作の中核。訳語のブレが致命的）
- 登場人物名のカナ表記

作業手順:
1. `tools/extract_terms.py` で原文から大文字始まりの語・頻出語を機械抽出して候補リスト化
2. 候補に訳語を割り当てて `glossary.yml` を作成
3. **既訳の訳語は参照しない**（訳語単体に著作権は原則及ばないが、独創的な訳語の模倣は避ける）

### Step 3: リポジトリ雛形とツールチェーン

想定構成:

```
blindsight-ja/
├── README.md                 # 原著クレジット・既訳案内・進捗表(自動生成)
├── LICENSE                   # CC BY-NC-SA 4.0 全文
├── NOTICE.md                 # 原著・原典URL・ライセンス継承の説明
├── CONTRIBUTING.md           # 貢献手順＋法的誓約事項
├── STYLEGUIDE.md             # 文体・表記ルール
├── glossary.yml              # 用語集(単一の情報源)
├── source/                   # 原文(英語)。EPUBから抽出、無改変
├── segments/                 # 翻訳単位ファイル (章ごと)
├── tools/
│   ├── extract.py            # EPUB/HTML → segments (安定ID採番)
│   ├── build.py              # segments → HTML / EPUB
│   ├── check_glossary.py     # 用語集との整合チェック
│   ├── check_style.py        # 表記ゆれ・禁則チェック
│   └── stats.py              # 章別進捗率を算出
├── dist/                     # ビルド成果物 (gitignore 推奨)
└── .github/
    ├── workflows/ci.yml
    ├── ISSUE_TEMPLATE/translation-fix.yml
    ├── PULL_REQUEST_TEMPLATE.md
    └── CODEOWNERS            # 章ごとのレビュー担当
```

### Step 4: セグメント化の設計 ★コミュニティ修正の肝

**段落単位で安定 ID を振る**のが要点。これにより「特定の1段落だけを直す PR」が小さな diff になり、レビューしやすくなる。

推奨フォーマット: **gettext PO 形式**

理由:
- `msgid` に原文、`msgstr` に訳文という対訳構造が標準化されている
- Poedit / Weblate / OmegaT などの既存 GUI ツールがそのまま使える
- `fuzzy` フラグで「要レビュー」を表現できる
- `msgfmt` で構文検証、未訳カウント・進捗率算出が自動でできる
- 翻訳者コメント (`#`) に訳注や議論の経緯を残せる

ID 設計:
- `#: <章ファイル名>:<段落連番>` を参照コメントに入れる
- 原文は固定（書籍なので変化しない）ため連番で十分だが、**原文のハッシュを併記**しておくと抽出スクリプト改修時の取り違えを検出できる

代替案: 1段落1行の JSONL / TSV。diff は読みやすいが既存ツールの恩恵がない。**PO を推奨。**

### Step 5: コミュニティ修正ワークフロー

**提案経路を2段階にする**（敷居の低い入口と、確実な入口の両方を用意する）:

1. **Issue で提案**（初心者向け）
   テンプレート項目: セグメント ID / 現在の訳 / 提案する訳 / 理由（誤訳・不自然・用語不統一など）
2. **PR で直接修正**（慣れた人向け）
   `segments/*.po` を直接編集

**CI で自動チェック**（`.github/workflows/ci.yml`）:
- `msgfmt` による PO 構文検証
- `check_glossary.py`: 用語集に定義された原語が別訳になっていないか
- `check_style.py`: 文体（常体／敬体）の混在、表記ゆれ、全角半角
- textlint（日本語校正。小説なのでルールは緩めに調整）
- `stats.py`: 進捗率を算出し、PR にコメント＋README のバッジを更新
- `build.py` が通るか

**レビュー体制**:
- 章ごとに「章リード」を CODEOWNERS で設定
- マージ条件: メンテナ1名の approve（初期）→ 参加者が増えたら2名 approve
- 用語集の変更は影響範囲が広いので、別途 approve 要件を厳しくする

**貢献者への法的誓約**（`CONTRIBUTING.md` に明記＋PR テンプレのチェックボックス）:
- [ ] 既訳（創元SF文庫版）を参照・引用・流用していない
- [ ] 貢献内容を CC BY-NC-SA 4.0 で提供することに同意する
- [ ] 機械翻訳の生出力をそのまま投稿していない（利用した場合は明記し、必ず推敲する）
- DCO 方式（`Signed-off-by`）で署名を求めるのが軽量で運用しやすい

### Step 6: 試訳でワークフローを検証

全章に着手する前に、**プロローグ＋第1章のみ**を訳してパイプライン全体を回す。
ここで用語集・スタイルガイド・CI・ビルドの不備を洗い出して修正する。

## 8. リポジトリ運用上の注意（onepagers 配下に置く場合）

`CLAUDE.md` のダッシュボード更新ルールが適用される。新規プロジェクト追加時は以下4箇所を更新:

1. `<project>/index.html`
2. `<project>/dashboard.md`
3. ルート `dashboard.md`（プロジェクト一覧テーブル）
4. ルート `index.html`（カード）

ただし **onepagers は公開リポジトリのため、「まずプライベートで」という方針と矛盾する。**
別途プライベートリポジトリを作る案を第一候補として、Step 1 でユーザーに確認すること。
